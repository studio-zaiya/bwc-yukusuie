# ゆくすいえ フレンドリー監査

攻めのレビューが「面白いか、すごいか」を意見で見るのに対し、これは**初見の人の手順を1歩ずつたどる**監査。意見ではなく、詰まった場所と理由を記録する。

## 0. なりきる人（2人。両方でたどる）
- **Aさん**：38歳、共働き。家づくりは初めてで、建蔽率も付帯工事も知らない。スマホのゲームは少し遊ぶ。審査員として、ひとりで5〜10分だけ遊ぶ
- **Bさん**：55歳。ゲームはほとんど遊ばない。PCは仕事で使う。文字が多いと読まずに飛ばす
- どちらも、事前の説明を読んでいない。動画も見ていない

## 1. 手順
- 実機を、タイトルの「家づくりを体験する」から最後までたどる（入口は1つ。人間の回答11/6）。ひとりプレイで
- 画面が変わるたびにスクリーンショットを撮り（webapp-testing スキルがあれば使う）、`out/friendly/<順番>-<画面>.png` に残す
- 各画面で、次の4つの問いに Aさん・Bさんとして答える。答えが「いいえ」なら、その場所を記録する
  1. **何をすればいいか**、3秒でわかるか（押すもの・書くものが一目でわかる）
  2. **どこを見ればいいか**、わかるか（主役が一番大きく、目が迷わない）
  3. **いま何が変わったか**、わかるか（押したあと、家・お金・世界線のどこが変わったかが見える）
  4. **どう進めばいいか、あとどれくらいか**、わかるか（工程の線、時計、「あと〇問」）

## 2. 必ず確かめること
- **案内（スポットライト）**：出るべきときに出るか（初めてその部品が出てきた瞬間）。指している位置がずれていないか。読み終わる前に消えないか。飛ばせるか。2回目以降は出ないか。一度に3つ以上の案内を重ねていないか
- **一度に読ませる量**：1つの吹き出し・札は2行まで。画面全体で、読まないと進めない文が多すぎないか（Bさんが飛ばしても進めるか）
- **専門用語**：建蔽率、容積率、付帯工事、地盤改良、ローン特約、施主検査、上棟、増工、別途など。初めて出る所に、ひとことの説明（押すと出る小さな「？」でもよい）があるか。説明が長すぎないか
- **待ち時間**：担当者やAIの返事を待つあいだ、何が起きているかわかるか（骨組みの表示、「少し考えてみますね」）。押せないボタンは押せない見た目か
- **失敗しても大丈夫か**：押し間違えたとき戻れるか。「こだわらない」「おまかせ」で進めるか。自由入力を空のまま進めるか
- **終わりがわかるか**：レポートまでたどり着いたとき、「終わった」「持ち帰れる」とわかるか。保存・印刷の方法がわかるか
- **動きを減らす設定**：減らしても、何が起きたかが伝わるか

## 2.5 見える・重ならない（視認性の最低ラインを、数えて確かめる）
目で見るだけでなく、スクリプトで測る。基準はWebのアクセシビリティの指針（WCAG 2.2）と、このプロジェクトのデザインコード。

**画面の大きさ**：1920×1080 だけでなく、**1280×720、1366×768、1440×900**（ノートPCとブラウザの帯を除いた広さ）でも撮る。重なりや見切れは、狭い画面で起きる
- **重なり**：文字を含む要素どうし、ボタンと文字が重なっていないか（例：工程の線の「1年後」に「？」のボタンがかぶる）。要素の外枠の矩形を取得して、重なりを自動で検出する
- **見切れ**：文字が枠からはみ出す、省略されて読めない、横に画面の外へ出ていないか
- **字の大きさ**（デザインコード）：本文16px以上、主要な数字・札の名前24px以上。補足の小さな字（「審査の目安」など）も12px未満にしない。計算されたフォントの大きさを全要素で測り、下回るものを一覧にする
- **文字と背景のコントラスト**（WCAG 1.4.3）：ふつうの文字は 4.5:1 以上、大きな文字（24px以上、または太字で約19px以上）は 3:1 以上。薄い灰色の補足文字が紙色の上で読めないことが多いので、特に見る
- **ボタン・アイコン・線のコントラスト**（WCAG 1.4.11）：押せる部品の輪郭やアイコンは、背景と 3:1 以上
- **押す大きさ**（WCAG 2.5.8）：押せるものは最低 24×24px。主な操作（「つぎへ」、札、選択肢）は 44×44px 以上を目安に。隣のボタンと近すぎて押し間違えないか
- **拡大**（WCAG 1.4.4）：ブラウザで200%に拡大しても、文字が重ならず、操作できるか
- **色だけに頼らない**（WCAG 1.4.1）：夫婦の色は形の印（■●◆）、会社は形（四角・三角・丸・六角）でも区別できるか
- 道具：Playwright で各画面を開き、要素の矩形とフォントの大きさを集めるスクリプトを一から書く。コントラストは axe-core（npm の開発用の依存として使ってよい）の結果を使う。結果は `out/friendly/visibility.md` に、画面ごとの違反の一覧で残す

## 2.6 録画とスクリーンショットに、個人の情報を写さない
- 動画用の録画やスクリーンショットでは、ブラウザの**ブックマークバー、タブ、アカウントのアイコン、拡張機能**を写さない。録画専用のブラウザのプロファイル（ブックマークなし）か、全画面表示（F11）で撮る
- 画面の一部を撮るときも、端に個人のハンドルや勤務先の名前が入っていないか、書き出したあとに確かめる

## 2.7 レポート（PDF・印刷）も、初見の人の目で
レポートは「もらってうれしい紙」で、本物の打ち合わせに持っていくもの。画面と同じ深さで点検する。基準は `docs/REPORT_v2.md`。
- **持ち帰りたいか**：表紙を見て、自分たちの家のレポートだと分かるか（呼び名、わが家の絵）。冷蔵庫に貼りたい・担当者に見せたい、と思えるか
- **構成**：ページを順にめくって、「わが家の答え → 担当者に渡す1枚 → 選ばなかった世界線」の流れが分かるか。各ページの見出しだけで中身が想像できるか
- **読める量**：1つのカードの文が3行を超えていないか。同じ調子の長文（労いの決まり文句など）が並んでいないか。Bさんが見出しと数字だけ拾っても意味が通るか
- **専門用語**：地盤改良、別途、ローン特約などに、ひとことの説明があるか
- **レイアウト**：ページのはみ出し（表が下の注記やページ番号に重なる）、途中で切れる表、下半分の大きな空白、カードの大きさと中身の不釣り合いがないか。A4で印刷したとき（PDFと、ブラウザの印刷の両方）に同じに出るか
- **文字**：本文9.5pt以上、補足8pt以上。本文が灰色で薄くないか（紙色との対比4.5:1以上）。金額の書き方（万円、小数1桁）がそろっているか
- **担当者に渡す1枚**：3ページ目だけを切り取って渡しても、担当者に意味が通るか（初めて会う担当者になりきって読む）
- 道具：レポートをPDFに書き出し、各ページを画像にして見る（`out/friendly/report-p1.png` 〜 `p4`）。はみ出しは、各要素の矩形がページの枠の内側にあるかをスクリプトで確かめる

## 3. 守ること
- 事前に「何が起きるか」を予告する案内は足さない（CLAUDE.md：事前に説明しない）。操作の説明は足してよい
- 案内を増やしすぎない。直し方の第一候補は「画面そのものをわかりやすくする」、次が「案内を1つ足す」
- 発案元を区別する：直し方の案はClaudeの案として出す

## 4. 出力の形
1. 詰まった場所の一覧（重い順）：画面／Aさん・Bさんのどちらが／4つの問いのどれで詰まったか／何秒迷ったか（目安）／直し方の案（画面を直す・案内を足す・言葉を直す）
2. 案内（スポットライト）の点検表：案内ごとに、出るタイミング・位置・長さ・飛ばせるか の ○×
3. 専門用語の一覧：用語／初めて出る画面／説明の有無／説明の案（20字以内）
4. 「最初の60秒」の体験の文章（Aさんとして、時刻つきで何を見て何を思ったか）
5. レポートの点検（ページごと：構成・読める量・レイアウト・文字・担当者に渡す1枚）
6. 見える・重ならないの違反一覧（画面の大きさごと。重なり／見切れ／字の大きさ／コントラスト／押す大きさ）
7. よかった所（残すべき理由があるものだけ）
